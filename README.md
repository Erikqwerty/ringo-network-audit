# Сетевой аудит Ringo MDM

Набор bash-скриптов: проверяет, что сервер Ringo MDM правильно опубликован за reverse proxy и что сеть
пропускает трафик Apple MDM. Результат — HTML-отчёт для клиента и текстовые логи.

> **Неофициальный проект.** Личный инструмент автора, не связан с правообладателем Ringo MDM и не
> поддерживается им. Использует только эндпоинты, описанные в открытой документации
> ([docs.ringomdm.ru](https://docs.ringomdm.ru)), и стандартные протоколы (SCEP, Apple MDM).
> «Ringo» — товарный знак своего владельца; название используется только для указания совместимости.

Что проверяется:

- **Ringo** (`modules/ringo`): TLS 1.2/1.3, полнота цепочки сертификатов, срок и отзыв (OCSP/CRL),
  все публичные эндпоинты по схеме API нужной версии, websocket агента, реакция WAF, ложные
  срабатывания WAF на настоящих телах запросов устройств, DPI/ТСПУ на пути, отпечаток прокси,
  разбор tcpdump, сравнение с прошлым аудитом.
- **Apple** (`modules/apple`): APNs (5223/443, HTTP/2 до api.push.apple.com), активация, ADE и
  Apple Business, OCSP/CRL, NTP, признаки SSL-inspection.
- **Мониторинг** (`modules/monitor`): как `mtr` — параллельные пробы целей с историей задержек и потерь.

## Быстрый старт

```bash
./audit.sh                                    # интерактивное меню
./audit.sh --full https://mdm.example.com     # полный аудит: всё сразу (≈2–3 мин)
./audit.sh --ringo https://mdm.example.com --dpi
./audit.sh --apple --role client
./tests/run.sh                                # самопроверка без сети
```

Результат — папка `results/<домен>_<дата>_<время>/`:

| Файл | Что внутри |
|---|---|
| `report.html` | отчёт: один файл, открывается офлайн; у каждой проверки — «Подробнее» с командой и ответом |
| `ringo.txt`, `apple.txt` | текстовый вывод модулей |
| `details/` | подробности каждой проверки: команды, запросы, ответы, разбор (из них — окна «Подробнее») |
| `responses/` | заголовки и тела ответов сервера на каждую пробу |
| `swagger_server.json` | схема API, если сервер её отдаёт |
| `monitor/` | сырые пробы мониторинга |
| `ringo_capture.pcap` | захват трафика (с `--capture`) |

Пересобрать отчёт без повторных проверок: `./audit.sh --rebuild results/<домен>_<дата>_<время>`.

## Режимы и параметры

`./audit.sh --help` — полный список. Основное:

| Параметр | Действие |
|---|---|
| `--full [URL]` | Ringo со всеми проверками (`--scep-proxy --dpi`, WAF) + Apple (`--all`, обе роли) + мониторинг 60 с |
| `--internal` | запуск из разрешённой подсети: веб-интерфейс и API должны открываться |
| `--capture IFACE` | tcpdump во время проверки (нужен sudo); захватывайте на физическом интерфейсе, не на VPN |
| `--compare <папка>` | таблица расхождений с другим аудитом, например эталонного сервера |
| `RINGO_TOKEN=<JWT>` | точная версия Ringo через `/api/v1/version` (переменной окружения, чтобы токен не попал в логи) |
| `--duration S` / `--count N` | длительность мониторинга |

Модули можно запускать и напрямую: `modules/ringo/run.sh --help`, `modules/apple/run.sh --help`.

## Версии Ringo и схема API

Модуль Ringo сначала скачивает схему с сервера (`/api/v1/documentation-json`). Если она закрыта, он
определяет версию по маршрутам (`PUT /agent/checkin` есть только в 3.x) и берёт схему из `schemas/`.
Эндпоинты, которых нет в схеме этой версии, не проверяются.

Снимки копятся сами: схема сервера, которой ещё нет в `schemas/`, сохраняется туда — с `RINGO_TOKEN`
как `swagger_<версия>.json`, без него как `swagger_3.x_<дата>_<хеш>.json` (переименуйте, когда узнаете
версию). Отключить — `--no-save-schema`. Для закрытого сервера берётся самая свежая точная версия
семейства; если схема сервера совпала со снимком точной версии, скрипт называет эту версию.

Снимки swagger в репозиторий не входят (`.gitignore`): после клона `schemas/` пуста, и первый прогон
по серверу с открытой схемой её заполнит. Пока снимка нет, закрытый сервер проверяется по
встроенному списку эндпоинтов, без фильтра по версии. Свой файл можно передать через `--swagger`.

Swagger описывает ответы не полностью (в 2.4.4 у `PUT /mdm/checkin` — только 200), поэтому ответы
приложения на пробы объясняются ещё и по `schemas/known_responses.tsv`: операция, код, фрагмент
сообщения и что это значит. Встретили в «Подробнее» «код не описан» — допишите строку туда.

## Требования

macOS или Linux, bash 3.2+, `curl`, `openssl`, `perl`. Желательно: `dig`, `nc`, `python3` или `jq`
(разбор схемы API), `tcpdump` (захват). Без необязательных утилит соответствующие проверки
пропускаются или упрощаются.

## Структура

```
audit.sh                 точка входа: меню, запуск модулей, --full, отчёт
lib/                     общее: ui.sh (вывод, счётчики, формат строк), util.sh, menu.sh, runner.sh
modules/<модуль>/run.sh  аргументы → lib/*.sh (общие функции) → checks/ по порядку номеров
modules/<модуль>/checks/ проверки: папка на раздел отчёта, файл на проверку (см. ниже)
modules/monitor/         мониторинг
report/                  build.sh (HTML из логов), style.css, app.js — встраиваются в один файл
schemas/                 known_responses.tsv; снимки swagger по версиям Ringo (в .gitignore)
tests/                   run.sh и фикстуры
results/                 результаты аудитов (в .gitignore)
```

Проверки модуля Ringo (`modules/ringo/checks/`), в порядке выполнения:

```
00_header/         шапка: маршрут, IP сервера и ваш, версия Ringo и схема API, запуск захвата
10_tls/            версии TLS, цепочка, проверка клиентом, срок, OCSP/CRL, имена SAN, порт 80
20_endpoints/      эндпоинты Ringo через прокси; массовые 503; примечания
30_socketio/       polling-handshake и websocket upgrade агента
40_waf/            эталон и тестовые строки (--no-waf-probe отключает)
50_device_bodies/  настоящие тела запросов устройств через WAF
60_dpi/            DPI / ТСПУ: локальный TCP, SNI, «заморозка» потока, DNS (--dpi)
70_fingerprint/    веб-сервер, прокси, заголовки, CDN, WAF по сигнатурам
80_pcap/           разбор захвата (--capture / --pcap)
90_compare/        сравнение с прошлым аудитом (--compare)
99_summary/        что требует внимания, итог и код возврата
```

Модуль Apple устроен так же: `00_header/`, `10_hosts/` (хосты Apple), `20_ntp/`, `90_verdict/`
(вердикт по сценариям), `99_summary/`.

Каждый файл проверки начинается с комментария: что проверяется, почему это важно, когда какой итог
(OK / WARN / FAIL). Дальше — условие запуска (`(( DPI_PROBE )) || return 0`), функции, нужные только
этой проверке, и сама проверка. Файл `00_section.sh` печатает заголовок раздела. Файлы подключаются
через `source` и делят переменные модуля: что проверка оставляет для следующих, указано в её шапке
(«Задаёт: …»).

Как добавить проверку: создайте `modules/<модуль>/checks/NN_раздел/NN_имя.sh` — он выполнится по
порядку номеров (сначала раздела, потом файла). Печатайте строки через `badge`, учитывайте результат через
`count СТАТУС "подпись для итога"`, подробности для окна «Подробнее» — через `det_*` из `lib/detail.sh`.
Формат строк описан в `lib/ui.sh`: по нему строится HTML-отчёт.

В отчёте: клик по строке или «Подробнее» — окно с командами и ответами; ← / → — соседняя проверка;
ссылка вида `report.html#m1-r5~d` открывает окно нужной проверки сразу.

## Безопасность

- Пробы WAF и тела устройств неинвазивны: заведомо невалидные данные, приложение ничего не создаёт.
  Запускайте только по инфраструктуре, на проверку которой у вас есть согласие владельца.
- В `results/` попадают адреса, сертификаты, ответы и трафик серверов клиентов. Папка исключена
  из git — не добавляйте её принудительно.
- Скрипты предоставляются «как есть», без гарантий; за последствия запуска отвечает тот, кто запускает.
